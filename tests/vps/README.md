# tests/vps — одноразовый стенд Full-тира на арендованном VPS

Уровень **T5**: то, что нельзя проверить ни юнитами, ни в QEMU — потому что нужен настоящий
интернет-путь между роутером и сервером.

```sh
scp tests/vps/provision-lab.sh root@<vps>:/root/
ssh root@<vps> 'bash /root/provision-lab.sh'      # печатает готовые ссылки
ssh root@<vps> 'bash /root/provision-lab.sh --teardown'
```

## Почему «ключей от сервера» ни у кого просить не надо

Частое заблуждение: чтобы протестировать Reality или Hysteria2, нужен доступ к чьему-то серверу с
готовыми ключами. Это не так — **ключи генерируются**, и генерирует их тот же `sing-box`:

| Что нужно | Откуда берётся |
|---|---|
| Пара ключей Reality | `sing-box generate reality-keypair` (в схеме: `private_key` — server only, `public_key` — client only) |
| UUID пользователя | `sing-box generate uuid` |
| `short_id` | случайные hex-байты (`openssl rand -hex 4`) |
| Пароль Hysteria2 и obfs | случайные (`openssl rand`) |
| Сертификат для Reality | **не нужен принципиально** — Reality занимает рукопожатие чужого сайта, в этом его смысл |
| Сертификат для Hysteria2 | self-signed, клиент идёт с `insecure=1` |

Домен тоже не нужен. Нужен только чистый VPS: 1 vCPU, 1 ГБ RAM, Debian или Ubuntu, публичный
IPv4, root по SSH-ключу.

## Что этот стенд даёт, чего не даёт `make qemu-netem`

Герметичный стенд уже поднимает НАСТОЯЩИЙ sing-box-сервер внутри netns и гоняет через него
трафик — то есть серверная сторона сама по себе давно автоматизирована. VPS добавляет ровно то,
что невозможно смоделировать на veth:

1. **PMTU и фрагментация.** В нашем TUN зашит `mtu 1500`. На реальном пути (PPPoE, оверхед QUIC,
   туннель провайдера) это может дать «мелкие сайты открываются, крупные висят». Это **главный**
   риск надёжности, ради которого VPS и берут.
2. **Reality против настоящего заимствованного SNI.** У Reality-инбаунда поле `handshake` —
   server only и **обязательное**: сервер реально ходит на заимствованный сайт во время
   рукопожатия, поэтому в изолированной VM (где эта цель недостижима) серверную часть Reality не
   поднять вообще.
   Отдельно: даже с настоящим сервером Reality требует, чтобы ClientHello доехал **байт-в-байт**.
   Сеть с прозрачным прокси или TLS-инспектором его переписывает, и клиент получает
   `reality verification failed` при исправном конфиге — это ограничение протокола, а не наша
   ошибка (подробности и как это установлено — в ADR 0004).
3. **Port hopping насквозь.** Скрипт заворачивает диапазон UDP-портов на слушающий порт через
   nftables — как это делают в реальности. Без серверной стороны клиентский `server_ports`
   проверяется только на уровне «конфиг валиден».
4. **Долгий прогон:** сутки без вмешательства, reboot роутера, реконнект при смене IP.

Чего он **не** проверяет: устойчивость к фильтрации. Ни один лабораторный сервер не скажет,
пропустит ли конкретный провайдер конкретный протокол — это видно только из той сети, где у
человека проблема.

## Почему это НЕ в CI

Постоянный CI-джоб против арендованного VPS — это секреты в репозитории, счёт каждый месяц и
чужая инфраструктура в критическом пути сборки. Против приоритета «минимум поддержки одним
человеком». Поэтому:

- **постоянная автоматизация остаётся герметичной** (`qemu-*` цели, они не зависят ни от чего
  внешнего и не протухают);
- VPS используется **окном**: подняли, прогнали чек-лист, записали результат в ADR, удалили.

Долговечен здесь не сервер, а **вывод**: закрытые пункты «не подтверждено живьём» и цифры замеров.

## Чек-лист прогона (в порядке важности)

- [ ] **MTU/PMTU**: крупные страницы и скачивание большого файла через оба протокола. Симптом
      проблемы — мелкое открывается, крупное висит. Если проявилось — это правка `mtu` в
      `SINGBOX_DEFAULTS`, и её нужно занести замером, а не на глаз.
- [ ] **Reality end-to-end**: трафик идёт, connectivity-probe подтверждает. Закрывает пункт 1
      раздела «что НЕ подтверждено живьём» в [ADR 0004](../../docs/kb/decisions/0004-multi-protocol-tiers.md).
- [ ] **Hysteria2 end-to-end** + то же с объявленной скоростью (Brutal): сравнить с
      «автоматически» на реальном канале.
- [ ] **Port hopping**: ссылка с диапазоном работает так же, как с одним портом.
- [ ] **Переключения из панели** между всеми тремя протоколами, с проверкой автооткатa на
      заведомо битой ссылке.
- [ ] **Сутки + reboot**: туннель встаёт сам, панель не врёт про здоровье.

Результаты — в ADR 0004, раздел «Замеры»/«что НЕ подтверждено живьём», как они получились.

## Результат первого прогона (2026-07-31)

- **Hysteria2 — подтверждён end-to-end**, включая port hopping: проба UP, внешний адрес равен
  адресу VPS, 10 МБ скачались целиком.
- **Reality — провалился, но не по нашей вине.** Тот же outbound, поле в поле как его генерирует
  движок, запущенный НА VPS, работает. Ключи проверены арифметически, `sing-box-tiny` и полная
  сборка ведут себя идентично, а провал воспроизводится и в QEMU, и напрямую с хоста разработчика.
  Диагноз: путь переписывает ClientHello (прозрачный прокси / TLS-инспектор), а Reality против
  такого не работает в принципе.

Поэтому `live-vps.sh` теперь ПЕЧАТАЕТ этот диагноз при `reality verification failed`: без него
провал читается как баг конфига, и человек уходит править то, что не сломано.
