# 🔧 Troubleshooting — куда смотреть

> [!tip] TL;DR
> 90% жалоб «нет интернета» решаются тремя командами: статус [[amneziawg|туннеля]], статус
> режима, последние логи. Начинай с них.

## Первые три команды

```bash
vpn-mode status                      # режим (HOME/TRAVEL) + общее состояние
awg show awg0 | grep handshake       # туннель живой? «N seconds ago» < 2 мин = ок
logread | tail -200                  # что случилось недавно
```

## По симптому

### «Нет интернета вообще»
1. `awg show awg0` — есть свежий handshake? Нет → проблема с [[amneziawg|туннелем]]/конфигом.
2. [[kill-switch]] работает как задумано: туннель упал → непрямой трафик дропается (не утечка).
   Это **не баг**, а защита. Чини туннель.

### «Сайт из direct-списка идёт через VPN, а должен напрямую»
Проверь, попал ли его адрес в [[dnsmasq-nftset|direct]]:
```bash
nft list set inet fw4 direct         # есть ли там нужный IP
nslookup example.com                  # резолвится через наш dnsmasq?
```
Если домена нет в твоём direct-списке (или в импортированном community-списке) — его адрес
туда не попадёт. См. [[dnsmasq-nftset]].

**Адрес в наборе ЕСТЬ, а трафик всё равно идёт через VPN.** Значит сломана вторая половина моста:
метка ставится, а направлять помеченный трафик нечем. Спроси ядро напрямую — оно ответит честнее,
чем конфиг:
```bash
ip route get <IP-из-набора> mark 0x1   # ожидается dev <WAN>, а НЕ dev awg0/singtun0
ip rule show | grep fwmark             # правило направления должно быть
ip route show table 100                # в таблице direct должен быть default через WAN
```
Пусто? Верни правила одной командой (она же зовётся при загрузке роутера):
```bash
ucode -R /usr/share/cheburnet/engine/install/reapply.uc
```
Так выглядел реальный баг: правила policy-routing живут только в ядре и не переживали
перезагрузку, поэтому после каждого ребута direct-домены уходили в туннель при полностью зелёной
панели. Восстановление держит hotplug-хук `/etc/hotplug.d/iface/99-cheburnet` — если файла нет,
переприменение настройки из панели (смена режима) вернёт и его.

### «Реклама лезет»
Блокировку даёт **выбранный DNS-провайдер**, а не локальный список — проверь, что выбран
фильтрующий резолвер и что запросы реально идут через него:
```bash
uci get https-dns-proxy.cheburnet_doh.resolver_url   # какой резолвер выбран
nslookup ads.example.com                              # фильтрующий вернёт пустой/0.0.0.0
```
Не фильтрует → смени провайдера в панели (`ads`/`family`). Учти: реклама с общего CDN-домена
DNS-блокировкой не режется. См. [[adblock]], [[0005-dns-filtering-not-local-adblock]].

### «Клиент не слушается split-routing»
Возможно, у устройства **свой DoH** (Chrome, смарт-ТВ) — оно не резолвит через нас.
Это [[dns-and-routing#Зависимость от того, что клиент использует НАШ DNS|известный размен]]:
такой клиент уходит в туннель (fail-safe), прямого пути для доменов из списка у него не будет.

### Мастер вместо шага «Проверка роутера» показывает экран смены LAN-адреса

Это не баг — конфликт подсетей LAN/WAN, детект **до** запуска обычного мастера. Возникает,
когда cheburnet-router висит за другим роутером (каскад), и обе стороны используют одну и ту
же подсеть `192.168.1.0/24` — тогда policy routing и kill-switch не могут отличить «локальную»
сеть от «внешней» через LAN-интерфейс.

Как это работает:
1. При заходе на мастер (до preflight) фронтенд зовёт ubus-метод `check_lan_conflict` (anon,
   без токена) — движок сверяет `lan_cidr`/`wan_cidr` из `network.interface.*.status` через
   `cidr_overlap()` (сравнение сетевой части по меньшему из двух префиксов).
2. При конфликте ответ содержит `suggest_ip` — первый свободный кандидат из
   `192.168.{2,3,4,8,9,10,11}.0/24` (перебираются по порядку, каждый проверяется той же
   `cidr_overlap` против WAN), никогда не совпадающий с диапазоном WAN.
3. Экран `LanConflict.svelte` показывает оба CIDR и предложенный адрес; можно **пропустить**
   (конфликт останется — предупреждение будет разве что в основном preflight, который тоже
   блокирует на `lan_wan`) или **сменить LAN** — это зовёт `apply_lan_ip` (write, требует
   install-токен), который валидирует адрес (`valid_lan_ip`: строго `192.168.X.Y`, хост
   `1..254`), правит `network.lan.ipaddr` (сохраняя маску) и через 3 секунды перезапускает
   `network` — роутер станет доступен по новому адресу, старая сессия браузера оборвётся.

Если застрял на этом экране без явной причины — сверь `192.168.1.x` со своим апстрим-роутером
(тот, что раздаёт cheburnet-router интернет по WAN).

## Проверка плоскости данных

```bash
ip rule show                         # видны ли наши policy-routing правила
ip route show table 100              # таблица «напрямую через WAN»
nft list ruleset | less              # все правила фаервола и kill-switch
```

Поскольку весь [[data-plane]] — на нативных примитивах, всё **видно и проверяемо** командами.
Это прямое следствие «без чёрных ящиков» ([[0001-why-not-singbox]]).

## Логи установки

```bash
cat /tmp/cheburnet/install.log       # лог последней установки
cat /tmp/cheburnet/done              # маркер завершения
```

## Диагностический пакет (для тех, кто просит помощи)

Кнопка **«Собрать диагностику»** в панели (или из терминала — то же самое) собирает логи,
состояние сети, версии и конфигурацию в один текст:

```bash
ucode -R /usr/share/cheburnet/engine/install/diagnostics.uc          # человеку
ucode -R /usr/share/cheburnet/engine/install/diagnostics.uc --json   # для UI
```

**Секреты вырезаются до вывода.** Это не удобство, а требование безопасности: пакет уходит в
мессенджер, и без чистки вместе с логами уехали бы рабочие ключи VPN и пароль домашнего Wi-Fi —
причём человек был бы уверен, что «просто отправил логи». Вырезаются приватные и пресхаред-ключи
WireGuard/AmneziaWG (в том числе голые, без имени поля), пароли Hysteria2 и обфускации, UUID и
`pbk`/`sid` у Reality, пароли из JSON-конфигов sing-box, пароль Wi-Fi из UCI.

**Адрес и порт сервера остаются намеренно** — подключиться по ним нельзя, а без них причину не
найти. По той же логике остаются SNI, тип обфускации и сообщения об ошибках: это и есть материал
для диагноза.

Список того, что вырезано, печатается в шапке пакета, и панель показывает текст **до** скачивания.
Обещание «мы всё вычистили» без возможности посмотреть своими глазами непроверяемо — поэтому
пользователь видит ровно то, что отправит.

Домены прямого доступа **считаются, а не печатаются**: их список говорит о том, что человек
открывает, а для диагностики достаточно размера набора.

Куда смотреть в коде: чистка — чистая `redact()` (`engine/lib/redact.uc`, юниты
`engine/lib/tests/test_redact.uc`), сбор — `engine/install/diagnostics.uc`, сквозная проверка на
живой системе — секция «Диагностика» в `tests/qemu/install-v2.sh`. Роутер сам никуда пакет не
отправляет: токен бота в прошивке вытащил бы любой желающий, а в момент поломки исходящий доступ
как раз может не работать.

## Сброс настройки: что снимается, а что остаётся

Кнопка «Сбросить настройку cheburnet» (или `ucode -R engine/install/reset.uc`) — это **не удаление
программы**, и путать эти вещи вредно: человек нажимает её, ожидая чистый роутер, а получает
роутер без VPN, но с установленным пакетом.

**Снимается:** правила и наборы nft, ip-правила и таблица policy routing, NAT-зона; секции туннеля
в `network` (обе группы — AmneziaWG и sing-box, независимо от активного протокола); привязки
dnsmasq (наши ipset-секции, DoH-апстримы, `noresolv`); `https-dns-proxy` целиком; `sing-box`, если
Full-тир ставился (сервис, uci-секция, `config.json`); содержимое `/etc/cheburnet`.

**Остаётся:** пакеты (`apk del` — осознанно забота владельца), движок в `/usr/share/cheburnet`,
обработчик rpcd и веб-панель, Wi-Fi и пароль root. Панель после сброса открывается и показывает
мастер.

Два момента, оплаченных инцидентами:

- **network `restart`, а не `reload`.** `awg0` был дефолтным маршрутом; reload не возвращает
  WAN-дефолт после удаления интерфейса — netifd держит остаточный дефолт через мёртвый туннель, и
  роутер остаётся **без интернета**. Тот же урок, что в `rollback_all`.
- **Повторная настройка не требует SSH.** Install-токен одноразовый: успешная установка его
  снимает, а сброс удаляет вместе с каталогом. Из-за этого и «Настроить заново», и мастер после
  сброса доводили человека до последней кнопки и отвечали «токен не найден — запустите bootstrap по
  SSH». Теперь токен выдаёт ubus-метод `install_token` (auth=**admin**, access=**write** — он
  создаёт состояние, и называть это чтением было бы нечестно): панель зовёт его по осознанному
  действию владельца и ведёт в мастер ссылкой с токеном. Гейт остаётся строгим — значение обязано
  совпасть с файлом (0600, root-only), а анонимному тиру метод недоступен.

  Почему выпускает не сам сброс: **лежащий без спроса токен — это стоящий без нужды пропуск на
  установку.** Одно место выпуска после bootstrap'а, и только когда он действительно нужен.
  Повторный вызов отдаёт тот же токен, а не новый: иначе уже открытая у человека ссылка мастера
  умирала бы при каждом обновлении панели.
